## English

## Overview

Open ACE combines role-based access control (RBAC) with multi-tenant boundary enforcement:

- **6 roles** in the `UserRole` universe (`app/models/user.py:14-22`): `user`, `readonly`, `manager`, `tenant_admin`, `platform_admin`, plus the legacy `admin`
- **19 permissions** assigned through 4 built-in RBAC role definitions (`app/services/permission_service.py:72-113`, `DEFAULT_ROLES`)
- **10 authentication decorators** (see the inventory below) that cover login, admin tiers, machine access, and tenant boundaries
- One strict-mode switch, `OPENACE_PLATFORM_ADMIN_STRICT_MODE`, that narrows who counts as a platform admin

For the endpoint-by-endpoint view, see [API_PERMISSION_MATRIX.md](API_PERMISSION_MATRIX.md) (same directory, generated by `scripts/generate_permission_matrix.py`).

## Role Universe

The authoritative sources are `UserRole` / `ADMIN_ROLES` / `PERSISTABLE_ROLES` in `app/models/user.py:14-30` and `ROLE_GROUPS` in `app/constants/role_groups.py`.

| Role | Tenant scope | Persistable? | Description |
|------|--------------|--------------|-------------|
| `platform_admin` | All tenants | Yes | Platform administrator; can manage every tenant (whether legacy `admin` also counts depends on strict mode, see below) |
| `tenant_admin` | Own tenant only | Yes | Tenant administrator; must have a non-null `tenant_id` (DB constraint `chk_2332_tenant_admin_requires_tenant`) |
| `admin` (legacy) | System-wide for compatibility | **No** — excluded from `PERSISTABLE_ROLES`; existing accounts keep working, create/update/restore reject it | Legacy super-admin kept for backward compatibility (Issues #2286, #2332); migrate these accounts to `platform_admin` |
| `manager` | — | Yes | Team manager: 11 permissions (view/export across messages, analysis, users, quota, audit, content filter) |
| `user` | — | Yes | Regular user: 4 permissions (`view_dashboard`, `view_messages`, `view_analysis`, `view_quota`) |
| `readonly` | — | Yes | Dashboard viewing only (`view_dashboard`) |

`ADMIN_ROLES = frozenset({"admin", "platform_admin", "tenant_admin"})` is what "is an admin" means throughout the codebase (`User.is_admin`, ownership-check bypasses). For **display statistics**, roles collapse into three groups (`app/constants/role_groups.py`): admin (`admin`/`platform_admin`/`tenant_admin`), manager, and user (`user`/`readonly`).

The built-in RBAC permission matrix (19 permissions, from `DEFAULT_ROLES` in `app/services/permission_service.py:72-113`):

| Permission | admin | manager | user | readonly |
|------------|-------|---------|------|----------|
| view_dashboard | ✓ | ✓ | ✓ | ✓ |
| view_messages | ✓ | ✓ | ✓ | |
| export_messages | ✓ | ✓ | | |
| view_analysis | ✓ | ✓ | ✓ | |
| run_analysis | ✓ | ✓ | | |
| export_analysis | ✓ | ✓ | | |
| view_users | ✓ | ✓ | | |
| create_user / edit_user / delete_user | ✓ | | | |
| manage_permissions | ✓ | | | |
| view_quota | ✓ | ✓ | ✓ | |
| manage_quota | ✓ | | | |
| view_audit_logs / export_audit_logs | ✓ | ✓ | | |
| view_content_filter | ✓ | ✓ | | |
| manage_content_filter | ✓ | | | |
| admin_access / system_config | ✓ | | | |

`admin_access` acts as a superuser bypass — a role holding it passes every permission check (`Role.has_permission`).

Note that `tenant_admin` / `platform_admin` are admin-tier roles for decorator purposes (they satisfy `ADMIN_ROLES`); the `DEFAULT_ROLES` matrix above covers the non-admin tier plus the legacy `admin` entry that owns all 19 permissions.

## Authentication Decorators (10)

All definitions live in `app/auth/decorators.py` except `machine_access_required` / `machine_admin_required` (`app/routes/remote.py:1059-1088`) and `api_key_admin_required` (`app/auth/decorators.py:1984`). Usage counts are call sites under `app/` as of this writing:

| Decorator | Uses | One-line responsibility |
|-----------|------|-------------------------|
| `@admin_required` | 91 | Accepts any admin role (`admin`/`platform_admin`/`tenant_admin`) via session token or WebUI URL token; **deprecated** (Issue #2332) — migrate to `any_admin_required` or `platform_admin_required` |
| `@auth_required` | 51 | Requires a valid login; optional `ownership='session'` or `ownership='machine'` check that admin roles bypass |
| `@platform_admin_required` | 25 | Requires a platform admin per strict mode; logs legacy `admin` acceptance as deprecated |
| `@same_tenant_or_platform_admin` | 8 | Tenant-scoped resource access: a tenant admin for the resource's own tenant, or any platform admin (tenant keyword governance endpoints) |
| `@machine_access_required` | 9 | Remote-machine access: system admin or a user assigned to the machine |
| `@same_tenant_user_required` | 8 | Stacked *below* an admin decorator; confines user-targeted admin endpoints (reset password, update, delete…) to the actor's tenant and protects platform-level accounts from tenant admins |
| `@machine_admin_required` | 4 | Remote-machine administration: system admin or the machine's designated admin |
| `@api_key_admin_required` | 4 | API-key management authorization (Issue #2327): resolves the authorized target tenant and sets `g.actor_scope`; see the dedicated section below |
| `@any_admin_required` | 4 | Any admin role, for non-cross-tenant operations (user management within own tenant, tenant-neutral config, audit access) |
| `@tenant_member_required` | 1 | Admin roles **plus** `manager`, for tenant-scoped alert endpoints (Issue #3082) |

Two markers are not counted as auth decorators: `@public_endpoint` flags intentionally unauthenticated routes for the security scanner, and `@security_annotated(reason=...)` flags endpoints whose ownership checks are inline rather than decorator-based.

For admin endpoints that take a `tenant_id` filter or act on a non-user resource, the decorators are paired with helpers in the same module: `resolve_tenant_scope()` / `require_tenant_scope()` (non-admins are tenant-scoped and denied when no tenant resolves — fail closed per Issue #1775), `enforce_requested_tenant_scope()`, `enforce_resource_tenant_scope()`, and `enforce_target_user_tenant()`. All fail closed on missing or inconsistent tenant ids instead of silently widening scope.

## Platform Admin Strict Mode

`OPENACE_PLATFORM_ADMIN_STRICT_MODE` (`app/auth/permissions.py:19-46`) controls who counts as a platform admin:

- **Strict off (default)**: both `platform_admin` and legacy `admin` pass `is_platform_admin_role()`
- **Strict on**: only `platform_admin` passes; legacy `admin` accounts stop being platform admins and get 403 on platform-admin endpoints

Operational rules:

1. The value is read once at startup and cached for the process lifetime — changing it requires a restart. `init_platform_admin_strict_mode()` is called from `create_app()` so the mode is frozen and logged before the first request
2. Migrate every remaining `role='admin'` account to `platform_admin` **before** enabling strict mode; `warn_if_strict_mode_locks_out_legacy_admins()` shouts at startup if strict mode would lock out legacy accounts
3. The flag governs checks that route through `is_platform_admin_role()` / `User.is_platform_admin()` (`platform_admin_required`, `same_tenant_or_platform_admin`, `resolve_admin_tenant_scope`). Code comparing role strings directly (e.g. `app/routes/mapping_rules.py`) is not affected — enabling the flag narrows authorization but does not remove the legacy role

See `docs/dev-notes/2332-admin-role-migration-runbook.md` for the migration runbook.

## Authentication

### Login Flow

1. Client sends `POST /api/auth/login` with `{username, password}`
2. Server validates credentials — bcrypt with **12 rounds** (`hash_password()` in `app/routes/auth.py:72`, same in `admin.py` / `tenant.py`)
3. Creates a session record with expiry
4. Sets the `session_token` cookie (HttpOnly, Secure over HTTPS)
5. Returns the user profile with role and `tenant_id`

### Rate Limiting

Failed login attempts are tracked in the `login_attempts` table (lockout thresholds come from security settings, default max 5 attempts). Security settings are cached for 60 seconds.

### Token Extraction

Session tokens are extracted from safe sources only — cookie → `Authorization: Bearer` header. Query-parameter session tokens are rejected per Issue #1896. A small allowlist of path prefixes (`/api/admin/`, `/api/remote/terminal/`, `/api/remote/vscode/`, `/api/workspace/`, `/api/projects`) accepts special URL tokens (WebUI v1/v2, proxy, browser tokens), validated by format and always audit-logged.

### Forced Password Change

If a user is marked `must_change_password=true`, every decorator blocks the request except the minimum endpoints: auth check, profile, change-password, logout, and password policy.

## Route Protection

- **Manage mode** (`/manage/*`) — all admin pages require an admin role; regular users and machine admins cannot reach them
- **API routes** — most `/api/*` blueprints authenticate via decorator or `before_request`; sensitive operations stack the admin-tier decorators above
- **Public routes**:
  - `/` — SPA catch-all (serves index.html)
  - `/api/auth/login` — login endpoint
  - `/api/auth/check` — auth status check
  - `/livez`, `/readyz`, `/metrics`, `/security-status` — probes and metrics (`/health` is deprecated and delegates to `/readyz`)

## Custom Permissions

Beyond the built-in roles, per-user permissions can be granted:

```python
PermissionService.grant_permission(user_id, 'export_analysis', granted_by=admin_id)
has_perm = PermissionService.has_permission(user_id, 'export_analysis')
```

Custom permissions are stored in the `user_permissions` table and combined with the user's role permissions.

## Multi-Tenant Isolation

When multi-tenant mode is enabled:

- Users are associated with a tenant via `tenant_id`
- Tenant quotas enforce per-tenant token and request limits; `QuotaEnforcementScheduler` runs every 60s, terminating exceeded sessions and generating alerts
- Tenant-aware boundaries cover users, projects, workspace sessions, session messages, daily usage aggregates, audit logs, remote machines, machine permissions, and quotas
- Non-admin user-facing APIs apply the authenticated tenant scope to session, project, usage, and audit queries
- Platform admins intentionally retain global operational visibility for support and incident response; every cross-tenant reach is audit-logged (`ADMIN_CROSS_TENANT_ACCESS`)

## API Key Tenant Authorization (Issue #2327)

The `tenant_id` parameter on API-key management endpoints is a **target selector, not an authorization credential**. The route-layer guard is `@api_key_admin_required`, which calls `resolve_authorized_target_tenant(actor, requested_tenant_id)`:

- **tenant_admin**: target tenant always comes from the auth context (`g.tenant_id`); omitting `tenant_id` uses the actor tenant (backward compatible), any other tenant returns 403
- **platform_admin / legacy admin**: must explicitly pass `tenant_id`; omitting it returns 400 (fail closed, no global list), cross-tenant operations are allowed and audit-logged
- Ownership checks on `PUT/DELETE /api/api-keys/<key_id>` return 403 (never 404) for keys outside the target tenant, so ids cannot be probed

The service/repository layers receive an immutable `ActorScope` (validated by `@require_actor_scope()`), so authorization cannot be bypassed by calling deeper layers directly. Everything fails closed: no default-tenant fallback, no silently ignored invalid `tenant_id`, no global listing.

Key storage, rotation, and proxy semantics are covered in [KEY_MANAGEMENT.md](../guide/KEY_MANAGEMENT.md); the full endpoint-by-endpoint permission tables are in [API_PERMISSION_MATRIX.md](API_PERMISSION_MATRIX.md).

## 概述

Open ACE 将基于角色的访问控制（RBAC）与多租户边界强制结合在一起：

- **6 个角色**构成角色宇宙（`app/models/user.py:14-22` 的 `UserRole`）：`user`、`readonly`、`manager`、`tenant_admin`、`platform_admin`，以及遗留的 `admin`

## 平台管理员严格模式

`OPENACE_PLATFORM_ADMIN_STRICT_MODE`（`app/auth/permissions.py:19-46`）控制谁算平台管理员：

- **关闭（默认）**：`platform_admin` 和遗留 `admin` 都能通过 `is_platform_admin_role()`
- **开启**：只有 `platform_admin` 通过；遗留 `admin` 账户不再是平台管理员，访问平台管理端点会得到 403

运维规则：

1. 该值在启动时读取一次并缓存整个进程生命周期——修改后必须重启。`create_app()` 会调用 `init_platform_admin_strict_mode()`，确保模式在首个请求前冻结并记入日志
2. 开启严格模式**之前**，先把所有 `role='admin'` 账户迁移为 `platform_admin`；`warn_if_strict_mode_locks_out_legacy_admins()` 会在启动时大声警告严格模式将锁死遗留账户
3. 该开关只影响经由 `is_platform_admin_role()` / `User.is_platform_admin()` 的检查（`platform_admin_required`、`same_tenant_or_platform_admin`、`resolve_admin_tenant_scope`）。直接比较角色字符串的代码（如 `app/routes/mapping_rules.py`）不受影响——开启开关收窄授权，但不会让遗留角色消失

迁移手册见 `docs/dev-notes/2332-admin-role-migration-runbook.md`。

## 认证

### 登录流程

1. 客户端发送 `POST /api/auth/login`，包含 `{username, password}`
2. 服务端验证凭证 —— bcrypt，**12 轮**（`app/routes/auth.py:72` 的 `hash_password()`，`admin.py` / `tenant.py` 相同）
3. 创建带过期时间的会话记录
4. 设置 `session_token` Cookie（HttpOnly，HTTPS 时为 Secure）
5. 返回含角色和 `tenant_id` 的用户资料

### 速率限制

失败的登录尝试记录在 `login_attempts` 表中（锁定阈值来自安全设置，默认最多 5 次）。安全设置缓存 60 秒。

### Token 提取

Session token 只从安全来源提取 —— cookie → `Authorization: Bearer` 头。按 Issue #1896，查询参数中的 session token 会被拒绝。少量路径前缀白名单（`/api/admin/`、`/api/remote/terminal/`、`/api/remote/vscode/`、`/api/workspace/`、`/api/projects`）接受特殊的 URL token（WebUI v1/v2、proxy、browser token），按格式校验并始终写审计日志。

### 强制改密

用户被标记 `must_change_password=true` 时，所有装饰器都会拦截请求，仅放行最小必要端点：认证检查、个人资料、修改密码、登出和密码策略。

## 路由保护

- **管理模式**（`/manage/*`）—— 所有管理页面要求管理员角色；普通用户和机器管理员无法访问
- **API 路由** —— 大多数 `/api/*` blueprint 通过装饰器或 `before_request` 认证；敏感操作叠加上述管理层级装饰器
- **公开路由**：
  - `/` —— SPA 全局捕获（提供 index.html）
  - `/api/auth/login` —— 登录端点
  - `/api/auth/check` —— 认证状态检查
  - `/livez`、`/readyz`、`/metrics`、`/security-status` —— 探针与指标（`/health` 已废弃，委托给 `/readyz`）

## 自定义权限

在内置角色之外，可以按用户授予自定义权限：

```python
PermissionService.grant_permission(user_id, 'export_analysis', granted_by=admin_id)
has_perm = PermissionService.has_permission(user_id, 'export_analysis')
```

自定义权限存储在 `user_permissions` 表中，与用户的角色权限合并计算。

## 多租户隔离

启用多租户模式时：

- 用户通过 `tenant_id` 关联到租户
- 租户配额强制执行每个租户的 token 和请求限制；`QuotaEnforcementScheduler` 每 60 秒运行一次，终止超额会话并生成告警
- 租户感知边界覆盖用户、项目、工作区会话、会话消息、每日用量聚合、审计日志、远程机器、机器权限和配额
- 非管理员用户可见 API 会把认证租户范围应用到会话、项目、用量和审计查询
- 平台管理员有意保留全局运维可见性，用于支持和故障处理；每次跨租户访问都写审计日志（`ADMIN_CROSS_TENANT_ACCESS`）

## API Key 管理租户授权（Issue #2327）

API Key 管理接口的 `tenant_id` 参数是**目标选择器，不是授权凭据**。路由层守卫是 `@api_key_admin_required`，它调用 `resolve_authorized_target_tenant(actor, requested_tenant_id)`：

- **tenant_admin**：目标租户始终来自认证上下文（`g.tenant_id`）；不提供 `tenant_id` 时使用 actor 租户（向后兼容），指定其他租户返回 403
- **platform_admin / 遗留 admin**：必须显式提供 `tenant_id`；缺失时返回 400（fail closed，不返回全局列表），跨租户操作被允许但写审计日志
- `PUT/DELETE /api/api-keys/<key_id>` 的所有权校验对目标租户之外的 key 返回 403（绝不返回 404），避免探测 key id

Service/Repository 层接收不可变的 `ActorScope`（由 `@require_actor_scope()` 校验），因此直接调用更深层也无法绕过授权。一切 fail closed：不回退默认租户、不静默忽略无效 `tenant_id`、不返回全局列表。

密钥存储、轮换与代理语义见 [KEY_MANAGEMENT.md](../guide/KEY_MANAGEMENT.md)；完整的按端点权限表见 [API_PERMISSION_MATRIX.md](API_PERMISSION_MATRIX.md)。
