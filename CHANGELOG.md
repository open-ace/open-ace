## [Unreleased]

### Added
- Sandboxed isolation level for interactive workspaces (Issue #3378): each user's qwen-code-webui runs in its own OpenSandbox pod instead of a local OS-account process — digest-pinned, image-allowlisted per-tier `webui_image`; identity is a per-instance token secret (no OS account, sudo chain, or host credentials — the control-plane credential denylist filters the pod env); the browser reaches the pod through a per-instance local port proxy that strips client credential headers, injects the server-resolved endpoint headers, and refuses bare CR/LF/NUL heads, non-token header names, and non-digit Content-Length values (request-side 400 / upstream-side 502); session history survives pod recycling via bounded per-user tar snapshots in an independent state root with a control-plane restore-confirmation record (an in-pod marker is never trusted as an export gate), atomic 0600 O_EXCL+fsync writes, tar validation before replace, and an unreadable-snapshot degrade path that suspends exports rather than treating the file as absent. The level is declared by a zero-pod fail-closed readiness probe (backend configured, tier exists, image pinned+allowlisted, tier API key present, no other live web process — per its heartbeat; an unreadable heartbeat root also refuses — callback URL egress-reachable); `workspace.required_isolation_level` is a floor, not a target — the launch form is the strongest verified form satisfying max(pin, request), so a configured webui_image flips default launches to pods even when the entrypoint pins `os_user`. Pod lifetime is clamped to its baked-in LLM proxy token (create and every renew, UTC), tokens mint per requester on the shared single-user instance, validation requires a live pod, and the boot-probe memo (per-tier, revocable, 1h TTL) upgrades the kernel dimension only on a positive gVisor identification and network_egress only on sidecar attestation — negative-only verdicts stay unsupported with explicit reason codes. Multi-replica safety: per-process heartbeat files (keyed by a per-process generation, not (boot_id, pid), which same-node containers share) are refreshed by a dedicated fixed-cadence 300s timer and removed at process shutdown (gunicorn worker_exit + atexit); the orphan reconcile refuses to sweep while a peer heartbeat is fresh or unreadable, and each orphan is isolated so one unreachable execd cannot abort the round. Server-returned sandbox ids are validated before joining control-plane record paths; the restore-confirmation record is written only for loaded/absent restore sources (never a degraded unreadable-snapshot start) and cleared only after a confirmed delete. The capability contract (policy revision 2026-09-12.2) reports the sandboxed level with per-level entry-point statuses (`sandboxed_entry_not_wired` for terminal/vscode/filesystem_api) and provisional markers on cold workers. See `docs/WORKSPACE_ISOLATION_CAPABILITIES.md` §6 for deployment requirements, the TTL chain, and the honest-limitation list (per-pod kernel/egress verification resets on control-plane restart, a failed probe on the tier, or the memo's 1h TTL; entry-point wiring and real-cluster end-to-end validation remain follow-ups #3379).
- Versioned capability contract for local interactive workspace multi-user isolation (Issue #3374): `GET /api/workspace/isolation-capabilities` reports what this deployment actually enforces (`local_workspace_multi_user`, `backend`, `isolation_level`, enforced/unsupported dimensions, per-entry-point coverage on supported snapshots, `policy_revision`), derived from live runtime state — including the WebUI launch-path readiness probe, so the contract and the launch gate can never disagree about the same host. The endpoint is read-only by construction (it never creates the WebUI manager, mints a token secret, or spawns cleanup greenlets). Interactive workspaces report at most `os_user` (per-user OS accounts on a shared kernel — never advertised as strong runtime isolation); probes never build (no npm runs) and privileged/reserved target accounts (uid 0 / uid < 1000, e.g. mapping `system_account` to `root`) are refused. See `docs/WORKSPACE_ISOLATION_CAPABILITIES.md` for semantics, reason-code reference, deployment requirements, and the audited list of remaining entry-point gaps split into follow-ups.
- Server-side isolation floor for workspace launches (Issue #3374): `GET /api/workspace/user-url` enforces `workspace.required_isolation_level` from config.json; when unset (or invalid — warned), the floor derives from what the deployment's launch-path probe actually verifies (`os_user` on healthy multi-user Docker AND package-method hosts, `none` on single-user or launch-degraded hosts). The `required_isolation` query parameter can only raise, never lower, that floor, and empty values count as absent. On probe-healthy multi-user deployments the default (parameterless) path fails closed: users without an explicit `system_account` mapping get a structured 400 (`identity_mapping_missing`) instead of a silently convention-derived launch — login no longer auto-backfills `system_account = username` in multi-user mode, no longer provisions username-convention OS accounts/homes for mapping-less users, cached instances whose launch account no longer matches the mapping are restarted under the current mapping, and the login-time background pre-start goes through the same gate (it never launches what the gate would reject). Multi-user installs now write an explicit `required_isolation_level: os_user` into config.json (docker entrypoint first-boot generation and the package installer), so an ops-induced launch-path degradation (removed wrapper, repointed webui_path) cannot silently drop per-user isolation; hosts without an explicit value derive the floor from the verified snapshot, which follows degradation downward while logging a WARNING (the derived floor is a mirror, not a hard floor — degraded hosts keep the previous default behavior rather than erroring). Rejections carry both reason namespaces (deployment-level + request-level). Single-user deployments are unaffected.

### Fixed
- Fresh multi-user production installs can now boot without manual migration steps (Issue #3397 — the multi-user acceptance run's declared deviation): a genuinely fresh database (no application schema AND no `alembic_version` table) used to be refused by the entrypoint, because `scripts/check_min_revision.py` exits 1 in production mode on exactly that state ("Fresh database detected in production"), so the documented DEPLOYMENT.md compose path could not start an empty database at all — the acceptance had to pre-initialize with a one-shot `alembic upgrade head && python3 scripts/init_db.py` container. The entrypoint now probes for the `alembic_version` table as well (quoted-heredoc python, so the #3399 raw-quote class cannot recur) and, when the database is provably fresh, self-initializes with the same two commands the deviation used before continuing the normal boot flow ("Fresh database detected — self-initializing schema and seed"). The branch is deliberately narrow: a database with existing schema or a recorded revision is never touched by it (the minimum-revision refusal and the regular upgrade path keep applying, and `init_db.py` still seeds only when no application schema existed at boot), and a failed probe reads as "unknown" — NOT fresh — so detection fails strict instead of bootstrapping blind over a database that might have data. **User-visible change**: a first `docker compose up` against an empty volume now starts instead of exiting; existing deployments are unaffected.
- Fixed (P0) the multi-user boot user-sync silently dying on every container start since 2026-09-08 (`5a20fd7bc`, auto-dev round 1): the SSH-sync hardening embedded python strings with RAW double quotes (e.g. `_log_sync_failure(username, "script_missing", ...)`) inside the bash DOUBLE-QUOTED `python3 -u -c` payload — bash stripped the quotes, split the argument at the first unquoted whitespace (~7.5KB in), and handed python a truncated program (SyntaxError, exit 1), while the mis-parsed pipeline tail kept the traceback out of `/app/logs/open-ace-user-sync.log` — zero-output silent death, the exact #3399 signature discovered by the #3385 acceptance runs (Issue #3399). Every boot's sync since that commit created NO OS accounts; deployments only appeared healthy because logins/WebUI launches provision accounts via the app-side `ensure_system_user` — the gap surfaced whenever a container was recreated (`--force-recreate`, image upgrade) and only the boot sync could restore `/etc/passwd`. The 49 payload lines are now properly `\"`-escaped, and a permanent guard test runs the invocation through REAL bash with a PATH-shimmed python3, asserting bash's expansion is byte-identical to the source extraction and parses — `bash -n` cannot catch this class (quotes stay balanced), and the functional harnesses' own unescape extraction masked it.
- Tenant-scoped OS isolation for shared projects: cross-tenant shell/agent access blocked and revocation now reclaims filesystem access (Issue #3396, found by the #3385 acceptance review). Previously every account — every tenant's — joined the single global `openace-shared` group and shared project directories were group-owned by it with 2775/664, so (1) any tenant's shell could `ls`/write any other tenant's shared project at the OS layer (the API layer's browse 400s never reach the terminal/agent channel), and (2) `PUT /api/projects/<id> {is_shared: false}` flipped only the database flag — ex-members kept full OS read/write. Shared project content is now group-owned by per-tenant groups `openace-shared-<tenant_id>` with dirs 2770 / files 660 (setgid kept for group inheritance; "others" bits dropped, so accounts of other tenants — which legitimately keep the global membership for namespace creation — get EACCES), while the global `openace-shared` group survives solely as the sticky `<base>/shared` namespace-root creation group. Revocation reclaims the directory to the creator (`chown -R creator` via the audited `openace-chown` wrapper + dirs 0700 / files 0600), fail-soft with a `permission_warning` in the response. Enrollment is tenant-aware everywhere accounts are provisioned (admin create/update/restore, login, WebUI launch, scheduler sync) and the Docker entrypoint's `/home`-glob group passes were replaced by a DB-driven sync that enrolls every active, non-deleted user into the global + own-tenant groups and reconciles pre-#3396 shared directories (left on the global group by existing deployments) onto their tenant group at startup (skipped per project when already normalized — one `stat` per project on steady-state boots). Review round 2 added two boot-time guarantees to that sync: a RECLAIM pass that fixes the fail-soft hole in revocation (a revoke that timed out after the database flip, or a soft-deleted shared project, left the directory group-owned and readable by the whole tenant forever) — a not-active-and-shared project directory is chowned back to its creator and stripped to 0700/0600 on restart, but (PR #3402 review, takeover hardening) ONLY when the directory provably was that row's own shared leftover: it must sit strictly inside a workspace base dir (never a base dir or the `<base>/shared` namespace root), must not overlap (equal to / contain / lie inside) any live shared project of any tenant, must carry the row's OWN tenant group, and a legacy pre-#3396 leftover on the global group is only reclaimed at the exact first-level `<base>/shared/<name>` shape — private registration had no path validation and the tenant-scoped uniqueness check never 409s cross-tenant, so a hostile private row pointing at foreign shared state must not be auto-chowned at boot (the API now refuses such registrations too: private paths must not be a base dir, lie in the shared namespace, or overlap another tenant's project) — and #3399-class de-silencing: the sync runs under `pipefail` with `python3 -u` and a nonzero Python exit surfaces as a loud WARNING line instead of dying silently behind `tee`, while the enrollment query itself excludes soft-deleted users (`deleted_at IS NULL`, the same classification as the user sync) so a restart can no longer re-grant a deleted user the tenant group the delete path removed. Deletion, deactivation and admin tenant-moves also drop the old tenant's group so those OS rights do not outlive the DB state. PR #3402 review hardening across the same surfaces: the boot sync is now AUTHORITATIVE for tenant-group membership — every existing `openace-shared-<t>` group is converged onto the DB's exact member list (`gpasswd -M`, per-member `gpasswd -d` when the desired list is empty, since shadow-utils treats `-M ""` as a no-op), so stale memberships from tenant moves/deactivations/deletes no longer survive a restart of the scheduler container (whose autonomous agents resolve supplementary groups against its own `/etc/group`); the global `openace-shared` group is deliberately left alone (deactivated accounts keep namespace-root creation — no content access). Enrollment, removal and reclaim now trust `system_account` only — the old `or username` fallbacks could cross tenant boundaries when an unmapped username collided with another user's OS account. The boot reconcile/reclaim chmod passes are batched (`-exec chmod ... {} +` — one fork per batch instead of per entry) so a node_modules-scale first-boot normalize no longer stalls service start for tens of minutes. The admin update route enrolls only users who end up ACTIVE (a PUT without `is_active` on a deactivated row used to re-grant the tenant group the deactivation dropped); the WebUI launch path fails CLOSED on tenant-lookup errors (a new `TENANT_UNRESOLVED` sentinel enrolls the global group only, instead of fail-opening into `openace-shared-0`). The `openace-chown` wrapper no longer sources `/etc/openace/openace-chown.conf` as shell code — the entrypoint writes it as data (one prefix per line, character-filtered `[A-Za-z0-9/._-]`, `/`-entries dropped) with the write itself inside the guarded `if` so an unwritable `/etc/openace` degrades to a warning instead of crash-looping under bash 5 `set -e`, and the root-run wrapper stat-validates the conf (root-owned, no group/world write bits) before use, falling back to the built-in prefixes otherwise. **User-visible change**: cross-tenant reads/writes of shared project directories via terminals/agents are denied at the OS layer, and unsharing a project immediately strips other members' filesystem access while the creator keeps hers. Residual (documented): directories of shared projects created before this change are normalized at the next container restart (or on demand via the fix-permissions endpoint / a re-share) — until then their content stays on the old global group, while new projects and every revocation are isolated immediately.
- Pinned multi-user OS account uids across container recreation (Issue #3390, found by the #3385 acceptance review): on an image upgrade or `compose up -d --force-recreate` the container starts from a fresh `/etc/passwd` while volume directories keep their numeric owners, and the entrypoint's DB sync re-useradded only the ACTIVE users with sequentially assigned uids — so a DEACTIVATED user's old uid necessarily landed on some active account, numerically handing that account the deactivated user's 0700 `/home/<user>` and `/workspace/<user>` (#3374's "A cannot enter B's private area", triggered by every image upgrade). The new `users.system_uid` column records each account's OS uid (written back by both the app-side `ensure_system_user` and the entrypoint sync at creation/re-sync), and every (re)creation passes it to `useradd -u` so uids are stable across recreations; the entrypoint additionally creates nologin placeholder accounts for deactivated/soft-deleted users that reserve their recorded uid so it can never be reassigned (a reactivated user's placeholder is upgraded back to `/bin/bash`), and processes pinned accounts before any unpinned `useradd` so a legacy account can never take a reserved uid. A pinned uid already owned by a different account name skips with a loud ERROR instead of silently renumbering — renumbering moves the file-ownership boundary between two users and is an administrator action, never automation; the scheduler container's account sync reads the same pins, so multi-container deployments stay consistent. **Upgrade note (declared residual)**: existing rows have no recorded uid and are deliberately not backfilled (the value was never persisted; guessing would be worse) — after upgrading, the first recreation records every ACTIVE user's assigned uid, and from the second recreation on all active uids are pinned. The residual is NOT time-bounded: a legacy DEACTIVATED/soft-deleted user never gets a pin (they are not re-synced), so their directories stay on an orphan uid (owner "UNKNOWN"), and any future account creation whose uid is still unpinned at `useradd` time can land on that number and inherit those directories numerically — the recording then pins that (already inherited) uid to the new user. Known closure, now implemented: a first-boot volume scan after the user-sync (`find /home <workspace base dirs> -maxdepth 3` collecting `stat -c %u`, dirs and files) adopts each observed uid >= 1000 that no account owns as an `openace-orphan-<uid>` nologin placeholder account (`useradd -M -s /usr/sbin/nologin -u <uid>`), so an unrecorded orphan uid is never handed to a future account; the adoption is idempotent (an adopted uid resolves via getent and is skipped) and degrades to a WARNING, never aborts the boot. Also hardened in review: the sync pipeline no longer masks a Python-side death (`pipefail` + `python3 -u`, so #3399-style silent kills surface as the WARNING line), and any Python exception inside the sync now exits nonzero instead of printing one line and ending with exit 0; active users left without an OS account by a collision skip or `useradd` failure abort the sync loudly instead of quietly, but only AFTER the project-directory pass — which still runs, so one failed account no longer blocks every other user's project-dir sync (the overall exit stays nonzero). The app-side auto uid assignment now excludes the DB-recorded active pins in addition to the /etc/passwd uids (fail-soft to the old plain `useradd` if the pin query fails), so a boot-sync failure can no longer let an unpinned account steal a recorded pin; the admin user-update route provisions the OS account only after the row write succeeds — so a NEW mapping's uid write-back actually lands — and only for users who end up active, so editing a deactivated user never re-shells their nologin placeholder; and the scheduler container's account sync now skips deactivated/soft-deleted users so it no longer strips the nologin shell off their placeholder accounts.
- Provisioned the multi-user shared-project namespace root at container startup (Issue #3379, gap found by the #3374 acceptance dry run): on a fresh volume nothing created `<workspace-base>/shared`, so the first `POST /api/projects` with `create_dir: true` ran `sudo -u <user> mkdir -p` against a root:root 0755 parent and failed with 403 for every user — the #3376 first-class `<base>/shared/<name>` namespace could never bootstrap. The Docker entrypoint's multi-user block now creates `<base>/shared` per workspace base dir (comma-separated `WORKSPACE_BASE_DIR` lists are iterated for this provisioning instead of mkdir-ing a literal `a,b` directory), owned by the `openace-shared` group with mode 3775 (setgid, so shared files inherit the group; sticky, so members cannot rename or delete each other's project directories). The provisioning is idempotent, only ever touches the root itself (never user data inside it), skips with a warning when the path collides with an account named `shared` **that already exists at container start**, degrades to a warning instead of crash-looping when the filesystem refuses it (e.g. root_squash NFS), and a post-DB-sync group-enrollment pass re-adds recreated users to `openace-shared` (sessions survive container recreation, and the sync's `useradd` adds no supplementary groups — without the pass those users kept getting 403 until re-login). The app side additionally refuses to provision workspace dirs for an account named `shared` in Docker multi-user mode (that path IS the namespace root; taking it over would break shared projects for the whole tenant). **User-visible change**: fresh multi-user deployments can create shared projects immediately; existing deployments get the root on their next container restart. Remaining gap (follow-up): package-method multi-user deployments (`install.sh`, base dir `/home`) still lack the equivalent provisioning — Docker deployments are the scope of this change.
- Fixed (P0) production images crash-looping on boot since 2026-09-05 (`1a67c04a7`, #3277 regression): the frontend integrity check globbed for a hardcoded `main.*.js`, but the vite build's real entry chunk is `index.<hash>.js` (named after its `index.html` input), so every `FLASK_ENV=production` boot failed the check and the gunicorn worker exited with code 3 — compose deployments and documented setups all hit it, discovered by the #3385 acceptance workflow's first real boot (Issue #3394). The check now derives the expected entry filename from the already-validated `.vite/manifest.json` (`index.html` → `file`, with traversal containment and non-empty validation) — the manifest is the single source of truth, with no legacy `main.*.js` fallback — and still fails closed in production when no valid entry exists. The check is surfaced as `entry.js` (was the misleading `main.*.js` in startup errors; `main.js` in the `/readyz` `frontend_build` payload). The `OPENACE_SKIP_FRONTEND_CHECK=1` escape hatch now also gates `/readyz` (previously the worker booted but readiness kept returning 503 under production security mode), and the frontend CI lane runs the check against the real `npm run build` output so checker/vite drift fails a PR lane instead of production boots.
- Fixed app-side configuration path resolution to honor `OPENACE_CONFIG_DIR` before falling back to `~/.open-ace` (Issue #3110). Upgrade note for custom SQLite deployments: the module-level default `ace.db` path now follows `OPENACE_CONFIG_DIR`; move an existing `~/.open-ace/ace.db` into the configured directory before upgrading, or set `DATABASE_URL` explicitly to retain the old database path. Docker Compose deployments use PostgreSQL and are unaffected.
- Hardened workspace entry-point boundaries for multi-user deployments (Issue #3376): terminal `status`/`attach`/`stop` and VSCode `status`/`stop`/`attach` now require session ownership instead of machine-level access alone — terminal endpoints allow platform admins, same-tenant tenant admins, and the session owner; VSCode endpoints follow the code-server proxy's existing role set (platform admins, same-tenant tenant admins, same-tenant machine-level admins, and the owner, who is now the requesting user rather than the machine creator). Terminal `status` no longer returns the agent-side bridge credentials to browsers; terminal `work_dir` and VSCode `project_path` are validated server-side (absolute, no traversal, outside system directories — note this rejects remote paths under `/opt`, `/var`, `/root` etc.); `/fs/browse` and `/fs/check-path` enforce the same home-subtree lock as write operations while keeping explicitly shared project paths reachable. Review round 2 closes two follow-ups found in runtime forensics: a shared project can no longer be registered on a path inside another user's home subtree (any depth, e.g. `<workspace>/<account>/.ssh`) or outside the creator's own roots (own home subtree or an already-open shared root), and the read-side filter drops any shared row inside a user home subtree regardless of stored creator; `/fs/check-path` admissibility is narrowed from the whole workspace base dirs to the user's own home subtree, the base dir itself, and first-level non-home children of a base dir, since its `exists`/`canCreate` probes amount to one-at-a-time existence enumeration under other users' homes (multi-level mkdir -p validation remains available inside the user's own home subtree). Review round 3 makes the shared directory a first-class citizen: round 2's creation-side ownership rule and the read-side home-subtree filter accepted disjoint sets (a shared path inside the creator's own home was created but never surfaced to other tenant members, and a fresh deployment could not bootstrap its first shared root since anchoring requires one to already exist), so new shared registrations now go through a dedicated non-home namespace `<base>/shared/<name>` that both sides accept — the namespace root itself is not registrable (container, not project), a namespace colliding with a real user home (an account literally named `shared`) is rejected fail-closed with an explicit message, and pre-existing clean first-level shared rows keep anchoring nested registrations.
- Fixed WebUI workspace tokens silently invalidating when `workspace.token_secret` was absent from config.json (Issue #3377): `WebUIManager` used to generate an ephemeral random secret per process, so tokens broke on every restart — and per-request token validation (which constructs a fresh manager) could not validate tokens at all in that state. The secret is now resolved as config.json value → `<config dir>/webui_token_secret` (0600, atomically created on first use) → generated once and persisted; concurrent first-boot races converge on one winner, malformed secret files are rebuilt, and unwritable config dirs degrade to the old in-memory behavior with a warning instead of silent breakage. Deployments that set the secret via the Docker entrypoint are unaffected.
- Fixed an environment-sensitive flaky in `tests/unit/test_webui_manager_42.py::test_webui_instance`: it asserted `WebUIInstance.is_alive() is False` for the hardcoded pid 12345, which fails on busy CI runners where that pid genuinely belongs to a live process (the `os.kill(pid, 0)` probe succeeds and the failed HTTP health check stays under the 10-failure death budget). The test now stubs the signal so every `is_alive()` branch — dead pid, alive pid via the fresh health cache, and no pid — is exercised deterministically regardless of the ambient pid table (Issue #3305)
- Extended per-test hang protection beyond the unit lanes: the `postgres` (single-process against the CI DB service; a healthy run measured 306.5s of its 480s budget) and `compatibility-smoke` pytest commands now run with the same `--timeout 300 --timeout-method thread --durations 20` flags as `python-core`/`python-min`, so a hung test dumps its stacks and fails loudly instead of silently burning the suite budget; the `performance` lane deliberately keeps no per-test timeout since its benchmarks are slow by design. Also restored the gradual-slowdown signal that #3281's budget raise traded away: `scripts/ci.py` now prints a non-fatal `WARNING` (and records a `suite_budget_warning` metrics event on nightly runs) whenever a suite completes above 75% of its budget, making budget-margin erosion visible in every CI log before it turns into an intermittent timeout (Issue #3282)
- Fixed the required `test (3.11)` CI lane intermittently dying with "Command exceeded 599s" on healthy runs: the `python-core` suite budget is raised 600s→1200s (matching `python-min`, #3240) because GitHub-hosted runner variance swings the same suite between ~289s and ~535s, so the old budget sat inside the variance band; both unit lanes now also run pytest with `--timeout 300 --timeout-method thread --durations 20` so a hung test dumps its stacks and fails loudly in bounded time instead of burning the whole suite budget undiagnosably (Issue #3280)
- Fixed the remote LLM-proxy failover loop deadlocking when a key resolver ignores `exclude_key_ids` and keeps returning an already-excluded key (e.g. a non-quota upstream 429): the handler now treats that as failover-pool exhaustion and returns 502 instead of retrying the same key forever, which could hang the process (Issue #2466)
- Fixed configuration persistence in docker-compose.multi-user.yml by adding `OPENACE_CONFIG_DIR` environment variable to ensure config persists to mounted volume when running as root (Issue #2235)
- Fixed install.sh script to automatically add required multi-user mode configurations (`user: "0"`, `OPENACE_ALLOW_ROOT_MULTI_USER=1`, `OPENACE_CONFIG_DIR`) when `WORKSPACE_MULTI_USER_MODE=true`
- Improved error messages in docker-entrypoint.sh when multi-user mode is enabled without root privileges, now recommending docker-compose.multi-user.yml as the easiest fix

### Changed
- Multi-user deployment documentation now recommends using docker-compose.multi-user.yml as the primary method
- The Docker image now defaults to the non-root `open-ace` user (uid 1000) via a `USER 1000` directive in the production stage, so `docker run`, docker-compose, and Kubernetes all run non-root without relying solely on the manifest `securityContext`. Multi-user workspace mode (which needs root for `useradd`/`chown`/`sudo -u`) is now an explicit, fail-fast opt-in: run as uid 0 (`docker run --user 0` / manifest `runAsUser: 0`) and set `OPENACE_ALLOW_ROOT_MULTI_USER=1`, otherwise the entrypoint exits with a clear error instead of silently swallowing permission failures.
- Kubernetes reference manifests now run the web pod as non-root with 3 replicas, HPA, and Prometheus scrape annotations restored; multi-user workspace deployments that require root must opt in via an explicit overlay.
- Docker-generated default config now enables AI autonomous development by default and only enables multi-user workspace mode when `WORKSPACE_MULTI_USER_MODE=true`.
- Documented the encrypted-secret upgrade path: existing deployments should set `OPENACE_ENCRYPTION_KEY` to the previous `SECRET_KEY` value before first restart after the security-hardening upgrade, then rotate in a planned maintenance window if desired.

## [1.0.0] - 2026-06-02

### Added
- **Self-hosted AI workspace**: Work Mode for AI sessions, prompt reuse, conversation history, and project context.
- **Remote Workspace and Remote Agent**: Run AI CLIs on development, staging, or GPU machines through a browser-managed remote agent.
- **Multi-CLI support**: Claude Code, Qwen Code, Codex, and OpenClaw adapters with session recovery, permission modes, and history sync.
- **API Key proxy**: Encrypt LLM API keys on the server and issue short-lived proxy tokens to local and remote sessions.
- **Browser development loop**: Remote terminal, directory browsing, and VSCode/code-server proxy support.
- **AI governance dashboards**: Token usage, cost analysis, quotas, alerts, anomaly detection, audit trails, and ROI visibility.
- **Compliance reporting**: Governance reports with JSON/CSV export paths and practical risk recommendations.
- **Enterprise administration**: Multi-tenant access control, roles, SSO-ready permission model, and Feishu/DingTalk integration paths.
- **Deployment options**: Docker Compose quick start, production deployment docs, Kubernetes reference, and reverse proxy guidance.
- **Open source readiness**: Apache 2.0 license, contributing guide, code of conduct, security policy, public roadmap, issue templates, CODEOWNERS, Dependabot, and beginner-friendly issue labels.
- **Bilingual documentation**: Chinese and English docs for architecture, deployment, development, API usage, integrations, Remote Workspace, Remote Agent, Kubernetes, and repository setup.

### Architecture
- Flask backend with SQLAlchemy repositories and Alembic migrations.
- React 18, TypeScript, Vite, Bootstrap 5, and Chart.js frontend.
- PostgreSQL and SQLite support for development and deployment workflows.
- Remote agent package with CLI adapters, WebSocket terminal support, and session synchronization.

### Deployment
- Docker Compose quick start with PostgreSQL.
- Source installation path for local development.
- Kubernetes deployment reference.
- Linux systemd and macOS launchd support for remote agents.
