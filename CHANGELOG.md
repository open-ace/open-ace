## [v2.1.0] - 2026-09-27

### Upgrade Notes
- **Workspace isolation configuration changed (Issue #3446).** Package and Docker installs convert existing configs automatically; source installs and read-only mounted configs must run `scripts/convert_workspace_isolation.py` (or edit by hand) before starting 2.1.0. Isolation of interactive workspaces is configured in one block, `workspace.isolation {"level": ..., "backend": ...}`, with the backends `shared` (level `none`), `plain` / `bwrap` (`os_user`) and `local-gvisor` / `local-kata` / `opensandbox` (`sandboxed`), plus optional `tier`, `limits` (`memory` / `cpu_percent` / `tasks`), `egress_allow` and `container_webui`. The keys it replaces — `multi_user_mode`, `required_isolation_level`, `os_user_confinement`, `sandbox_tier`, `confinement_*` — are rejected (the server refuses to start and names the replacement), as are a level/backend pair that does not belong together and a backend the install method cannot provide (`OPENACE_INSTALL_METHOD`, set by the Docker image and the package installer's units; the Docker install cannot run `bwrap`/`local-*`). Existing configs are converted by `scripts/convert_workspace_isolation.py`, which the package installer runs on fresh install, local upgrade and remote upgrade (before it rewrites sudoers) and the Docker entrypoint runs on every start (a read-only mounted config is not converted: the server then names each key to replace); each old key is read the way the old server read it: a tier with a `webui_image` in `sandbox-backends.json` (which ran pods whatever `multi_user_mode` said) or `required_isolation_level: sandboxed` becomes `opensandbox` with its tier, a floor above the old mode is kept by raising the backend, and an `os_user_confinement` value the old server refused stops the install instead of being guessed. Semantics: the declared level is the floor (a degraded launch path refuses launches instead of serving on the shared account); the backend is explicit (pods only for `opensandbox`, never inferred from `webui_image`; a backend that is not ready is reported unsupported with its reason, never replaced by another; the single shared pod is gone). The capability snapshot reports the same backend names (`shared` / `plain` / `bwrap` / `local-gvisor` / `local-kata` / `opensandbox:<tier>`), `isolation_backend_shared` replaces `multi_user_mode_disabled`, and it adds `install_method` and `available_backends` (policy revision `2026-09-26.3`). The root policy `/etc/openace/webui-confine.json` keys its container sections by backend (`local-gvisor` / `local-kata` with `image` + `runtime`, top-level `docker`), and `openace-webui-confine --backend` takes the backend names. Docker: `WORKSPACE_ISOLATION_BACKEND=shared|plain|opensandbox` replaces `WORKSPACE_MULTI_USER_MODE` / `WORKSPACE_REQUIRED_ISOLATION_LEVEL`.

### Added
- Workspace isolation admin guide in English and Chinese (`docs/en/WORKSPACE_ISOLATION.md`, `docs/cn/WORKSPACE_ISOLATION.md`, Issue #3446): the six isolation modes side by side, **which modes each install method allows** (the Docker install cannot run the confined or local-container sandboxes, and why), a minimal configuration for each mode, how to verify what is in force, and the common mistakes. The isolation capability reference and the sandbox-backends reference are now bilingual pairs under `docs/en/` and `docs/cn/` (previously `docs/WORKSPACE_ISOLATION_CAPABILITIES.md`, Chinese only, and `docs/SANDBOX_BACKENDS.md`, English only); the doc-executing tests run against both languages.
- Local Kata Containers sandbox for interactive workspaces (Issue #3438): `workspace.isolation {"level": "sandboxed", "backend": "local-kata"}` is the local-container form of #3431 Option 2 on a Kata runtime (Kata >= 3.32.0, `/dev/kvm`), reported as the `sandboxed` level with backend `local-kata`. A Kata guest cannot reach host UNIX sockets over virtio-fs, so ingress and egress are multiplexed as framed streams with per-stream credit windows over the container's stdin/stdout: the container keeps `--network none`, with no bridge network and no host firewall rules, and any framing violation ends the launch. `launch --probe --backend local-kata` verifies Kata positively from the host (docker's `State.Pid` is a hypervisor whose parent is the Kata shim for that container id, and the guest kernel differs from the host's). The root policy file's `local-kata` section names the Docker runtime; `io.containerd.kata.v2` works without a `daemon.json` entry.
- Local gVisor container sandbox for interactive workspaces without Kubernetes (Issue #3431, Option 2): `workspace.isolation {"level": "sandboxed", "backend": "local-gvisor"}` runs each user's WebUI in a Docker container on a registered gVisor runtime (`runsc` with `--host-uds=open`) from a digest- or ID-pinned image, as the user's OS account (`--user` + `--group-add`), with `--network none`, a read-only image root, dropped capabilities, `no-new-privileges`, memory/CPU limits, an RLIMIT_NPROC task bound enforced by the gVisor kernel, and only the user's home, `<base>/shared` and the log dir bind-mounted. It reuses the Option 1 root entry point, reverse-tunnel ingress, allowlist egress proxy and root-owned audit log; the WebUI environment reaches the container on stdin. `launch --probe` (root) verifies the docker CLI, the runtime, the local image, a gVisor guest kernel and host UNIX-socket access; the capability contract then reports the `sandboxed` level with backend `local-gvisor` and every dimension enforced, while keeping the os_user entry-point matrix, the OS-account identity gate and the local launch form (the OpenSandbox pod form is now selected by backend, not by level). A root parent process stays alive for the container's lifetime (signal forwarding, force-removal if sudo is killed, leftover-container and run-dir cleanup), requires `fs.protected_symlinks=1`, and an in-container watchdog stops the WebUI if the host-side supervisor disappears. Egress log: equivalent IP spellings canonicalized, and summaries past the byte ceiling are written at most once a minute.
- Optional confinement for `os_user` interactive workspaces (Issue #3431, Option 1): with `workspace.isolation {"level": "os_user", "backend": "bwrap"}`, each per-user qwen-code-webui runs in a systemd scope (`MemoryMax`/`MemorySwapMax=0`/`CPUQuota`/`TasksMax`) entered through `setpriv --init-groups --no-new-privs` with all capabilities dropped, inside bubblewrap with a read-only host root, empty tmpfs over `/tmp`, `/var/tmp`, `/run` and the workspace base (only the user's home and `<base>/shared` are bound back — other homes are invisible), and a private network namespace whose only way out is a host-side proxy that allows allowlisted `host:port` pairs (the Open ACE API / LLM proxy endpoints plus `workspace.isolation.egress_allow`) and logs every decision. The root entry point `/usr/local/bin/openace-webui-confine launch` validates typed arguments, builds every systemd property itself, refuses executables not listed in the root-owned `/etc/openace/webui-confine.json`, and takes the WebUI environment on stdin so the proxy token never appears on a command line. The capability contract reports backend `bwrap` with `resources` and `network_egress` enforced; a host that cannot confine refuses the launch (the declared level is the floor) instead of serving unconfined. The package installer installs the wrapper, the policy file and a `launch`-only sudoers rule. Real-Linux acceptance: `scripts/webui_confine_acceptance.py`.

### Security
- Messages API is tenant-scoped (Issue #3440): all six endpoints in `app/routes/messages.py` (`/api/senders`, `/api/messages`, `/api/messages/count`, `/api/conversation-history`, `/api/conversation-timeline/<id>`, `/api/conversation-details/<id>`) were guarded by authentication alone, so any user of any tenant could read every tenant's senders, message content and conversations. A blueprint gate now gives global scope only to platform admins, pins everyone else (including `tenant_admin`) to their own tenant, and returns 403 for a non-platform-admin without a tenant; another tenant's conversation looks like a nonexistent one. The module-global senders cache, shared by every caller, is gone and the service cache key includes the tenant.
- `tenant_admin` is scoped to its own tenant on all 14 `/api/analysis/*` endpoints (Issue #3442): global scope was decided with `is_admin_role()`, which includes `tenant_admin`, so tenant admins saw usage, rankings, conversation stats and anomalies across all tenants. Global scope now requires `is_platform_admin_role()`. Note: tenant admins' analysis pages now show only their tenant, and the legacy `admin` role is no longer global under strict mode.

### Performance
- Admin dashboard no longer rescans `daily_messages` on every request (Issue #3424, measured on PostgreSQL 14 with 484k messages / 604k stats rows): `GET /api/trend` 91 s → 23 ms, `/api/tools` 10.8 s → 2 ms, `/api/senders` 19 s → 7 ms, `/api/hosts` 3–22 ms; the slowest parameter-less admin GET is now 25 ms (was 19 s). Fixes found on the way: `daily_stats` accumulated NULL-sender duplicate rows on every refresh (603k copies of 67 groups), which **doubled trend totals**; `needs_refresh` was permanently true; `/api/summary` returned 500 and the usage summary stopped refreshing since 2026-08-21 when a tool had rows in both sources (mixed `date`/string types on PostgreSQL); unfiltered `SELECT DISTINCT` is replaced by a loose index scan.
- Tenant-scoped `/api/tools` and `/api/hosts` walk two new partial indexes instead of scanning `daily_messages` (Issue #3424): tenant admins' `/api/hosts` 2.9 s → 12 ms, `/api/tools` up to 3.1 s → 28 ms. Migration `20260926_002` builds `idx_messages_user_tool` and `idx_messages_user_host` `CONCURRENTLY` on PostgreSQL (writes are not blocked; an INVALID leftover is rebuilt). Code deployed ahead of the migration falls back to the old query.

## [v2.0.0] - 2026-09-25

Open ACE 2.0 turns the self-hosted workspace into a multi-user, sandbox-isolated platform: interactive and autonomous agents can now run in OpenSandbox (gVisor/Kata) pods, autonomous workflows gain an independent acceptance-verification phase, and enterprise identity (SAML SSO, DingTalk/Feishu org sync) and alerting landed. It is a major version because of the upgrade-affecting changes listed below.

### Breaking Changes / Upgrade Notes
- **Python 3.10+ is required** (#1935, #1936); Python 3.9 is no longer supported. Python 3.13 is supported for source and offline installs (#2219, #2240).
- **The Docker image runs as the non-root `open-ace` user (uid 1000)** by default (#1797). Mounted `./data`, `./config` and log volumes must be writable by uid 1000; multi-user workspace mode, which needs root, must use `docker-compose.multi-user.yml` (or explicitly opt in with `user: "0"` + `OPENACE_ALLOW_ROOT_MULTI_USER=1`).
- **Set `OPENACE_ENCRYPTION_KEY` before the first restart after upgrading.** Stored secrets are now encrypted with a dedicated key; existing deployments must set it to their previous `SECRET_KEY` value, or previously encrypted secrets cannot be decrypted (#2275, #2362).
- **Kubernetes reference manifests run the web pod non-root with 3 replicas + HPA**; deployments relying on root must opt in explicitly.
- **Autonomous development is enabled by default** in Docker-generated config, and the scheduler's global concurrency default rose from 3 to 10 with a new per-user cap (#2295, #2297).
- Upgrading still requires starting from at least the `baseline_2026_06_23` revision (enforced by `scripts/check_min_revision.py`); run `alembic upgrade head` as part of the upgrade.

### Added
- **Sandboxed agent execution**: a `SandboxProvider` contract (#2022) with Legacy POSIX, Remote Machine and OpenSandbox providers; the OpenSandbox backend runs autonomous agents in gVisor or Kata pods with attestation-derived capabilities, fail-closed policy translation, CNI-enforced egress, orphan reconciliation and a TTL reaper (#2023, #3205). Per-task HOME/TMP/XDG isolation and cgroup-v2 resource policy (`scripts/setup-cgroup-v2.sh`) harden the local provider (#2020).
- **Agent state carry across ephemeral sandboxes**: the CLI session transcript is exported/imported per session line so `--resume` works for Claude Code, Codex, Qwen Code and ZCode across milestones (#3237, #3263, #3325, #3329, #3330).
- **Independent acceptance verification** for autonomous workflows: a verifier on a dedicated merged-main checkout, five mechanical gates (negative-test, legacy, call-chain, deployment, regression), scope gate, verdict aggregation, owner/admin override, in-page acceptance report viewer and resume-with-feedback (#2335, #2344, #2346, #2658, #2701, #3005).
- Evidence-based autonomous pipeline: structured command/test evidence replaces agent-prose heuristics, verify-before-act merge readiness, per-domain test-evidence requirement (shadow-first), and CI auto-repair raised to 5 attempts (#2045, #2046, #2194, #2391, #2460).
- Autonomous operations: GLM usage-window 429s pause the workflow and auto-resume at the window reset (#2709, #2714), loop-detection aborts auto-resume (#3149), lazy dependency preparation for agent worktrees (#2700), per-workflow `max_changed_files_override` with a scope-exceeded retry banner (#2309), real-time activity summary + heartbeat (#1734), final diff stats (#1717) and dedicated timeline icons for all milestone types (#3044).
- **SAML SSO provider** alongside OIDC, with frontend management (#3191, #3196).
- **DingTalk and Feishu integrations**: org sync, identity resolution for imported sessions, alert bots and a unified notification & integration settings page (#1768, #1787, #2384, #2632).
- **Alerting**: signed, asynchronous alert webhooks with duplicate-delivery cooldown, a global unread alert badge, a test-alert button and scheduler execution-health alerts (#1771, #1807, #3039, #3093, #3115, #3152).
- Personal files browser with upload/download/delete and recursive search, multi-user sudo compatible (#1779, #1878, #1928).
- ROI analysis with explicit, tenant-configurable assumptions, estimation labels and a per-user dimension; response-time metrics in trend analysis (#1757, #1854, #3092, #3111).
- Shared-project permission-change audit log and tenant-scoped OS isolation for shared projects (#2888, #3402).
- External proxy-token governance on the shared LLM-proxy path, and a default-off external identity capability probe for workspaces (#3423, #3415).
- Model selection for terminal sessions (#1976), remote projects in the WebUI project picker (#2478), a create-project button on project management (#3373), and a one-command Remote Agent launcher script (#2254).
- Kubernetes database backup CronJob with recovery documentation (#1853); migration authoring rules MIG001/MIG002 enforced in CI (#1706).
- Pre-built images are published to GitHub Container Registry on every release (`ghcr.io/open-ace/open-ace`, tags `vX.Y.Z`, `X.Y.Z`, `X.Y`, `X`, `latest`; linux/amd64). `docker-compose.yml`, the Kubernetes manifests and the docker-method installer now default to this image; previously they referenced `openace/open-ace` / `open-ace:latest`, which were never published.
- Sandboxed isolation level for interactive workspaces (Issue #3378): each user's qwen-code-webui runs in its own OpenSandbox pod instead of a local OS-account process — digest-pinned, image-allowlisted per-tier `webui_image`; identity is a per-instance token secret (no OS account, sudo chain, or host credentials — the control-plane credential denylist filters the pod env); the browser reaches the pod through a per-instance local port proxy that strips client credential headers, injects the server-resolved endpoint headers, and refuses bare CR/LF/NUL heads, non-token header names, and non-digit Content-Length values (request-side 400 / upstream-side 502); session history survives pod recycling via bounded per-user tar snapshots in an independent state root with a control-plane restore-confirmation record (an in-pod marker is never trusted as an export gate), atomic 0600 O_EXCL+fsync writes, tar validation before replace, and an unreadable-snapshot degrade path that suspends exports rather than treating the file as absent. The level is declared by a zero-pod fail-closed readiness probe (backend configured, tier exists, image pinned+allowlisted, tier API key present, no other live web process — per its heartbeat; an unreadable heartbeat root also refuses — callback URL egress-reachable); `workspace.required_isolation_level` is a floor, not a target — the launch form is the strongest verified form satisfying max(pin, request), so a configured webui_image flips default launches to pods even when the entrypoint pins `os_user`. Pod lifetime is clamped to its baked-in LLM proxy token (create and every renew, UTC), tokens mint per requester on the shared single-user instance, validation requires a live pod, and the boot-probe memo (per-tier, revocable, 1h TTL) upgrades the kernel dimension only on a positive gVisor identification and network_egress only on sidecar attestation — negative-only verdicts stay unsupported with explicit reason codes. Multi-replica safety: per-process heartbeat files (keyed by a per-process generation, not (boot_id, pid), which same-node containers share) are refreshed by a dedicated fixed-cadence 300s timer and removed at process shutdown (gunicorn worker_exit + atexit); the orphan reconcile refuses to sweep while a peer heartbeat is fresh or unreadable, and each orphan is isolated so one unreachable execd cannot abort the round. Server-returned sandbox ids are validated before joining control-plane record paths; the restore-confirmation record is written only for loaded/absent restore sources (never a degraded unreadable-snapshot start) and cleared only after a confirmed delete. The capability contract (policy revision 2026-09-12.2) reports the sandboxed level with per-level entry-point statuses (`sandboxed_entry_not_wired` for terminal/vscode/filesystem_api) and provisional markers on cold workers. See `docs/en/WORKSPACE_ISOLATION_CAPABILITIES.md` §6 for deployment requirements, the TTL chain, and the honest-limitation list (per-pod kernel/egress verification resets on control-plane restart, a failed probe on the tier, or the memo's 1h TTL; entry-point wiring and real-cluster end-to-end validation remain follow-ups #3379).
- Versioned capability contract for local interactive workspace multi-user isolation (Issue #3374): `GET /api/workspace/isolation-capabilities` reports what this deployment actually enforces (`local_workspace_multi_user`, `backend`, `isolation_level`, enforced/unsupported dimensions, per-entry-point coverage on supported snapshots, `policy_revision`), derived from live runtime state — including the WebUI launch-path readiness probe, so the contract and the launch gate can never disagree about the same host. The endpoint is read-only by construction (it never creates the WebUI manager, mints a token secret, or spawns cleanup greenlets). Interactive workspaces report at most `os_user` (per-user OS accounts on a shared kernel — never advertised as strong runtime isolation); probes never build (no npm runs) and privileged/reserved target accounts (uid 0 / uid < 1000, e.g. mapping `system_account` to `root`) are refused. See `docs/en/WORKSPACE_ISOLATION_CAPABILITIES.md` for semantics, reason-code reference, deployment requirements, and the audited list of remaining entry-point gaps split into follow-ups.
- Server-side isolation floor for workspace launches (Issue #3374): `GET /api/workspace/user-url` enforces `workspace.required_isolation_level` from config.json; when unset (or invalid — warned), the floor derives from what the deployment's launch-path probe actually verifies (`os_user` on healthy multi-user Docker AND package-method hosts, `none` on single-user or launch-degraded hosts). The `required_isolation` query parameter can only raise, never lower, that floor, and empty values count as absent. On probe-healthy multi-user deployments the default (parameterless) path fails closed: users without an explicit `system_account` mapping get a structured 400 (`identity_mapping_missing`) instead of a silently convention-derived launch — login no longer auto-backfills `system_account = username` in multi-user mode, no longer provisions username-convention OS accounts/homes for mapping-less users, cached instances whose launch account no longer matches the mapping are restarted under the current mapping, and the login-time background pre-start goes through the same gate (it never launches what the gate would reject). Multi-user installs now write an explicit `required_isolation_level: os_user` into config.json (docker entrypoint first-boot generation and the package installer), so an ops-induced launch-path degradation (removed wrapper, repointed webui_path) cannot silently drop per-user isolation; hosts without an explicit value derive the floor from the verified snapshot, which follows degradation downward while logging a WARNING (the derived floor is a mirror, not a hard floor — degraded hosts keep the previous default behavior rather than erroring). Rejections carry both reason namespaces (deployment-level + request-level). Single-user deployments are unaffected.

### Fixed
- Cross-user symlink escape in the file API (Issue #3410): `POST /api/fs/upload` derived its final target with `realpath(join(validated_dir, filename))`. realpath follows a symlink in the last component, and the follow-up check only compared the workspace-base prefix and dropped the home-subtree lock, so a user could place a same-named symlink in their own home pointing at another user's file and the root branch (Docker multi-user) would overwrite the victim's file (reproduced: 200 response that also echoed the victim's absolute path). Upload now descends from the home root one component at a time with `O_NOFOLLOW|O_DIRECTORY` directory fds, creates the temp file inside that fd with `O_EXCL|O_NOFOLLOW`, `fchown`s it and replaces the entry with `renameat`, which replaces the directory entry rather than a symlink target and removes the check-to-write TOCTOU window; the root branch also asserts the trust anchor with `fstat` (the home root belongs to the target account). A target name that is itself a symlink or an existing directory is an explicit 400 on both branches. **`download`, `delete-file` and `search` no longer operate by path either:** they validated the realpath and then opened, deleted or walked by path (download even opened the file in the response generator after the view returned), so under a root process swapping a component for a symlink between the check and the operation could read or delete any file on the host. They now work relative to the same component-by-component directory fd: `open(O_NOFOLLOW|O_NONBLOCK)` plus an `fstat` regular-file check (a FIFO cannot hang the request), `unlinkat`, and `os.fwalk` (symlinks themselves are skipped under root). In the non-root package install, `openace-write-as` and `openace-rm` perform every filesystem probe, write and delete after the user/prefix check through `runuser` as the target account (`openace-rm` used to run the final `rm` as root; `openace-write-as` ran its `-L`/`-d` probes as root and before the prefix check, leaking the type of arbitrary paths). `openace-write-as` also rejects symlinks (exit 5) and directories (exit 6), writes atomically with `mktemp` + `mv -fT`, and exits right after its INT/TERM trap cleans up. Both wrappers carry a capability marker, and the routes **fail closed on upload/delete** when the installed version lacks it. When a wrapper rejects early, an upload no longer turns into a 500 from manually closing an already-broken stdin. Under a root process, a user with no mapped `system_account` whose username equals another user's `system_account` no longer gets any home root, and an account named `shared` (including same-named users from SSO or org sync) never gets the shared-project namespace root `<base>/shared` as its home root in any deployment. uid resolution is a single `getpwnam` (account names starting with `-` are no longer parsed by `id` as options). Fixed in the same batch: `POST /api/fs/create-directory` gets the home-subtree lock it always lacked (same creatable set as check-path); single-file `/api/fs` paths, `/api/fs/home` and the default `search` root use per-base home roots, since on multi-base deployments (`WORKSPACE_BASE_DIR=/a,/b`) the old single-base helper produced the literal `"/a,/b/<account>"` and these endpoints all returned 400; `<base>/<account>` is tightened from 0755 to 0700 (matching `/home/<account>`; old volumes converge at startup and login provisioning, only for directories owned by that account, with the shared namespace root explicitly skipped); login provisioning under root sets owner and mode of `<base>/<account>` and its `.qwen` through directory descriptors.
- Dropped the "others" permission bits from the multi-user shared-namespace root `<base>/shared` (3775 → 3770; sticky and setgid kept): the root is group openace-shared, which every active account joins for namespace creation, but the old others r-x additionally let ANY non-member process on the host (other containers' agents, host services) enumerate the root and read shared project NAMES — metadata only (content access always required the per-tenant group), yet project names can be sensitive. Existing deployments are re-normalized on the next container boot (the provisioning is idempotent, and the unconditional chgrp+chmod also converges mode drift). Declared residual, documented in the acceptance handbooks: because namespace creation is a global right, cross-tenant members can still list the root via the group r-x — per-tenant name secrecy is not achievable in this design, while content access stays fenced by the per-tenant `openace-shared-<tenant_id>` groups (2770/660).
- Hardened the boot-time tenant shared-group convergence against two edge shapes in its `getent`-driven member filter: (1) the numeric-suffix guard for `openace-shared-<t>` groups used bare `str.isdigit()`, which ACCEPTS non-ASCII digits — a root-created `openace-shared-<unicode-digits>` lookalike passed the guard and the convergence emptied it member by member (no such tenant exists in the DB); the suffix must now be ASCII digits. (2) A transient NSS failure (`getent passwd` exit code neither 0 nor 2 — socket timeout, sssd restart, nscd hiccup) used to drop a PRESENT member from this boot's `gpasswd -M` list, silently removing their tenant content access until the next boot; the lookup is now retried once, and a member whose presence stays ambiguous after the retry skips that group's convergence entirely for this boot with a loud warning — never a list built on an unreliable answer (that either poisons `gpasswd -M` with a missing account, the shadow-utils rejection, or strips a member who is actually present). Both shapes self-heal on the next boot.
- Fresh multi-user production installs can now boot without manual migration steps (Issue #3397 — the multi-user acceptance run's declared deviation): a genuinely fresh database (no application schema AND no `alembic_version` table) used to be refused by the entrypoint, because `scripts/check_min_revision.py` exits 1 in production mode on exactly that state ("Fresh database detected in production"), so the documented DEPLOYMENT.md compose path could not start an empty database at all — the acceptance had to pre-initialize with a one-shot `alembic upgrade head && python3 scripts/init_db.py` container. - Hardened workspace entry-point boundaries for multi-user deployments (Issue #3376): terminal `status`/`attach`/`stop` and VSCode `status`/`stop`/`attach` now require session ownership instead of machine-level access alone — terminal endpoints allow platform admins, same-tenant tenant admins, and the session owner; VSCode endpoints follow the code-server proxy's existing role set (platform admins, same-tenant tenant admins, same-tenant machine-level admins, and the owner, who is now the requesting user rather than the machine creator). Terminal `status` no longer returns the agent-side bridge credentials to browsers; terminal `work_dir` and VSCode `project_path` are validated server-side (absolute, no traversal, outside system directories — note this rejects remote paths under `/opt`, `/var`, `/root` etc.); `/fs/browse` and `/fs/check-path` enforce the same home-subtree lock as write operations while keeping explicitly shared project paths reachable. Review round 2 closes two follow-ups found in runtime forensics: a shared project can no longer be registered on a path inside another user's home subtree (any depth, e.g. `<workspace>/<account>/.ssh`) or outside the creator's own roots (own home subtree or an already-open shared root), and the read-side filter drops any shared row inside a user home subtree regardless of stored creator; `/fs/check-path` admissibility is narrowed from the whole workspace base dirs to the user's own home subtree, the base dir itself, and first-level non-home children of a base dir, since its `exists`/`canCreate` probes amount to one-at-a-time existence enumeration under other users' homes (multi-level mkdir -p validation remains available inside the user's own home subtree). Review round 3 makes the shared directory a first-class citizen: round 2's creation-side ownership rule and the read-side home-subtree filter accepted disjoint sets (a shared path inside the creator's own home was created but never surfaced to other tenant members, and a fresh deployment could not bootstrap its first shared root since anchoring requires one to already exist), so new shared registrations now go through a dedicated non-home namespace `<base>/shared/<name>` that both sides accept — the namespace root itself is not registrable (container, not project), a namespace colliding with a real user home (an account literally named `shared`) is rejected fail-closed with an explicit message, and pre-existing clean first-level shared rows keep anchoring nested registrations.
- Fixed WebUI workspace tokens silently invalidating when `workspace.token_secret` was absent from config.json (Issue #3377): `WebUIManager` used to generate an ephemeral random secret per process, so tokens broke on every restart — and per-request token validation (which constructs a fresh manager) could not validate tokens at all in that state. The secret is now resolved as config.json value → `<config dir>/webui_token_secret` (0600, atomically created on first use) → generated once and persisted; concurrent first-boot races converge on one winner, malformed secret files are rebuilt, and unwritable config dirs degrade to the old in-memory behavior with a warning instead of silent breakage. Deployments that set the secret via the Docker entrypoint are unaffected.
- Fixed an environment-sensitive flaky in `tests/unit/test_webui_manager_42.py::test_webui_instance`: it asserted `WebUIInstance.is_alive() is False` for the hardcoded pid 12345, which fails on busy CI runners where that pid genuinely belongs to a live process (the `os.kill(pid, 0)` probe succeeds and the failed HTTP health check stays under the 10-failure death budget). The test now stubs the signal so every `is_alive()` branch — dead pid, alive pid via the fresh health cache, and no pid — is exercised deterministically regardless of the ambient pid table (Issue #3305)
- Extended per-test hang protection beyond the unit lanes: the `postgres` (single-process against the CI DB service; a healthy run measured 306.5s of its 480s budget) and `compatibility-smoke` pytest commands now run with the same `--timeout 300 --timeout-method thread --durations 20` flags as `python-core`/`python-min`, so a hung test dumps its stacks and fails loudly instead of silently burning the suite budget; the `performance` lane deliberately keeps no per-test timeout since its benchmarks are slow by design. Also restored the gradual-slowdown signal that #3281's budget raise traded away: `scripts/ci.py` now prints a non-fatal `WARNING` (and records a `suite_budget_warning` metrics event on nightly runs) whenever a suite completes above 75% of its budget, making budget-margin erosion visible in every CI log before it turns into an intermittent timeout (Issue #3282)
- Fixed the required `test (3.11)` CI lane intermittently dying with "Command exceeded 599s" on healthy runs: the `python-core` suite budget is raised 600s→1200s (matching `python-min`, #3240) because GitHub-hosted runner variance swings the same suite between ~289s and ~535s, so the old budget sat inside the variance band; both unit lanes now also run pytest with `--timeout 300 --timeout-method thread --durations 20` so a hung test dumps its stacks and fails loudly in bounded time instead of burning the whole suite budget undiagnosably (Issue #3280)
- Fixed the remote LLM-proxy failover loop deadlocking when a key resolver ignores `exclude_key_ids` and keeps returning an already-excluded key (e.g. a non-quota upstream 429): the handler now treats that as failover-pool exhaustion and returns 502 instead of retrying the same key forever, which could hang the process (Issue #2466)
- Fixed configuration persistence in docker-compose.multi-user.yml by adding `OPENACE_CONFIG_DIR` environment variable to ensure config persists to mounted volume when running as root (Issue #2235)
- Fixed install.sh script to automatically add required multi-user mode configurations (`user: "0"`, `OPENACE_ALLOW_ROOT_MULTI_USER=1`, `OPENACE_CONFIG_DIR`) when `WORKSPACE_MULTI_USER_MODE=true`
- Improved error messages in docker-entrypoint.sh when multi-user mode is enabled without root privileges, now recommending docker-compose.multi-user.yml as the easiest fix

### Changed
- Workspace isolation capability contract `policy_revision` bumped to `2026-09-16.1` (Issue #3410): in `entry_points`, `filesystem_api` goes from `partial` to `enforced` (the fix above plus a per-operation review), and `terminal`/`vscode` move from `partial` to the new status `remote_machine_scope`. Their old partial reasons (terminal tokens not bound to the session owner, VSCode owner taken from the machine creator) were already fixed by #3376 / PR #3380 without updating the matrix, but `enforced` would be wrong too: both run on the remote machine as that machine's agent account, outside the local `os_user` level, governed by machine ACLs, session ownership and tenancy. New `entry_point_details` give each entry point its `scope`, `covered_by_isolation_level`, per-operation `roots` and `symlink_policy`, `access_control`, plus `limitations` (real gaps that count toward admission) and `residuals` (known, accepted properties that do not), so integrators can tell "meets the chosen level", "remote scope" and "real gap" apart; an unknown `status` or an unreviewed `policy_revision` must fail closed. `filesystem_api` upload/download/delete-file/search declare `symlink_policy: never_followed_with_elevated_privilege` (below the home root no symlink is followed with more privilege than the target account); other operations are `resolved_then_rejected_if_outside`; `residuals` lists the shared project root, the package-install wrapper prerequisite and unmapped users. Sandboxed snapshots keep each entry point's `limitations` and append `sandboxed_entry_not_wired`, and `filesystem_api` no longer inherits the host-tree boundary/residuals. Docs §4 (entry-point matrix) is rewritten against the current implementation with the gaps closed by #3376/#3380 removed, and §7 adds an executable admission example that a unit test runs verbatim.
- Multi-user deployment documentation now recommends using docker-compose.multi-user.yml as the primary method
- The Docker image now defaults to the non-root `open-ace` user (uid 1000) via a `USER 1000` directive in the production stage, so `docker run`, docker-compose, and Kubernetes all run non-root without relying solely on the manifest `securityContext`. Multi-user workspace mode (which needs root for `useradd`/`chown`/`sudo -u`) is now an explicit, fail-fast opt-in: run as uid 0 (`docker run --user 0` / manifest `runAsUser: 0`) and set `OPENACE_ALLOW_ROOT_MULTI_USER=1`, otherwise the entrypoint exits with a clear error instead of silently swallowing permission failures.
- Kubernetes reference manifests now run the web pod as non-root with 3 replicas, HPA, and Prometheus scrape annotations restored; multi-user workspace deployments that require root must opt in via an explicit overlay.
- Docker-generated default config now enables AI autonomous development by default and only enables multi-user workspace mode when `WORKSPACE_MULTI_USER_MODE=true`.
- Documented the encrypted-secret upgrade path: existing deployments should set `OPENACE_ENCRYPTION_KEY` to the previous `SECRET_KEY` value before first restart after the security-hardening upgrade, then rotate in a planned maintenance window if desired.

- **Self-hosted AI workspace**: Work Mode for AI sessions, prompt reuse, conversation history, and project context.
